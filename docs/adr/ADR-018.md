# ADR-018 — Retirada de datos, systemd y logging estructurado

- **Estado:** Aceptada
- **Fecha:** 2026-11-12
- **Ámbito:** `src/motor/reconcile.py`, `src/motor/gc.py`, `src/motor/worker.py`,
  `src/motor/log.py`, `docs/systemd/`
- **Cierra:** D-005 (prune inerte), H1 (worker sin logs)

## Contexto

Tres huecos declarados tras el cierre del núcleo:

1. **El prune por conteo era inerte.** Cada versión publicada conserva su fila en
   `datasets`, y la regla dura de ADR-017 la protegía para siempre: "las últimas
   N" estaba implementada y probada, pero no actuaba en producción.
2. **`_mark_missing_datasets` solo auditaba.** Una fila huérfana (sin manifest)
   se re-auditaba en cada pasada (≈1 Hz) y dejaba la fila viva: spam en
   `audit_events` y un `503` permanente en la API sobre ese dataset.
3. **El worker no emitía logs.** `journalctl` mostraría una unidad vacía, así que
   el endurecimiento systemd no era verificable.

## Decisión

### A. Retirada de filas de `datasets` (hacer efectivo el prune)

1. **R1 — Orden.** Una versión se retira con **su versión física primero**
   (`rmtree`) y **su fila después** (`DELETE`), **en una sola transacción**
   (`BEGIN IMMEDIATE`). El orden inverso permitiría que
   `_rebuild_datasets_from_manifests` resucitara la fila desde un manifest que
   aún existe. `_retire_version` implementa ambos casos y audita dentro de la
   transacción; un fallo hace `ROLLBACK` y propaga.
2. **R2 — Convergencia.** `_mark_missing_datasets` pasa de *auditar y dejar* a
   *retirar la fila* (`reconcile_retire_dataset_row`), **salvo si un job la
   respalda**: una fila sin manifest pero con un job `claimed`/`queued`/
   `running`/`committed`/`archived` del mismo `job_key` se conserva, porque
   retirarla dejaría un resultado publicado que la API ya no puede describir. Es
   reversible: si el manifest reaparece, el rebuild la reconstruye.
3. **R3 — GC.** `prune_dataset_versions` retira (no solo protege) las versiones
   más allá de `keep`: con fila viva, fila y versión juntas (`gc_retire_dataset`,
   hash del manifest tomado **antes** del `rmtree`); sin fila, solo la versión
   (`gc_prune_dataset_version`, como antes). Protecciones intactas: `latest`, su
   destino y las versiones tocadas después de `now`.
4. **Orden en `reconcile`.** manifests → **completar jobs con dataset** →
   **retirar filas sin respaldo** → inputs perdidos → leases → movimientos →
   limpieza. Completar antes de retirar evita que un job recién recuperado pierda
   su fila.
5. **R4 — API sin cambios.** `GET /v1/datasets/{run_id}` sigue `404` si la fila
   se retiró y `503` si la fila existe pero falta el manifest.
6. **R5 — `jobs` no se toca.** Es historia/auditoría; un job `committed` puede
   apuntar a un `run_id` retirado.

### B. systemd: supervisor, nunca autoridad de datos

7. **Unidades de usuario** (`motor-worker.service`, `motor-api.service`) en
   `docs/systemd/`. `Type=exec` + `Restart=on-failure` + `KillMode=mixed`.
8. **Sin `WatchdogSec`.** El pipeline es de un solo disparo y no tiene fronteras
   de lote donde latir; un watchdog mataría CSVs legítimamente lentos y, con
   `MAX_ATTEMPTS=3`, los volvería fallos deterministas. Cablearlo es **T-013**.
9. **Sin timers.** Reconciliación y GC ya corren dentro del bucle del worker
   (ADR-008/017); un timer duplicaría la autoridad y rompería el "un solo reloj".
10. **Endurecimiento (§13).** `NoNewPrivileges`, `ProtectSystem=strict`,
    `ProtectHome=read-only`, `PrivateTmp`, `RestrictAddressFamilies=AF_UNIX`,
    `CapabilityBoundingSet=` vacío, `ReadWritePaths=%h/Yachay/data`. La API añade
    `IPAddressDeny=any`.
11. **Presupuestos de recursos** (`MemoryMax=8G`, `CPUQuota=200%`, …) son del
    perfil NORMAL, **valores de arranque no calibrados** (§16).
12. **Sin usuario `motor` ni `/opt`.** Corren como el operador; la variante de
    sistema con usuario dedicado requiere root y queda documentada, no ejecutada.
    El modo degradado (primer plano, sin unidad) sigue siendo válido.

### C. Logging estructurado del worker

13. **`src/motor/log.py`**: una línea JSON por evento a stdout (`journald` la
    captura tal cual), sin dependencias y con `flush` tras cada línea. Campos
    fijos `ts`, `component`, `event`.
14. **Nunca valores de datos.** Solo identificadores, estados, conteos y
    duraciones. Un test incrusta un valor centinela en el CSV y exige que no
    aparezca en el log.

## Consecuencias

- El prune **actúa**: una versión más allá de `keep` libera disco y su fila.
- Desaparece el spam de auditoría y el `503` permanente; la retirada es
  reversible desde el manifest si este reaparece.
- Un job nunca pierde su fila mientras lo respalde.
- `journalctl --user -u motor-worker` muestra progreso real (JSON por ciclo/job).
- Verificado en el host: unidades instaladas, worker `active`, logs JSON en
  journald, socket `0660` con la API respondiendo, reinicio automático tras
  `kill -9`, y sandbox que **bloquea** escrituras fuera de `data/`.

## Alternativas descartadas

- **Archivar (marcar) en vez de retirar:** exige `DDL` (no hay migraciones) y no
  libera disco, que es el objetivo.
- **Archivar moviendo el directorio:** rompe las tres rutas que asumen
  `processed/<dataset>/run_id=*/manifest.json` y tampoco libera disco.
- **Retirar siempre la fila huérfana:** dejaría un resultado publicado que la API
  no puede describir.
- **`Type=notify` + watchdog:** mataría CSVs lentos (ver decisión 8).
- **`User=motor` + `/opt`:** requiere root; fuera del alcance de "usuario".
- **Escribir el log con `logging`:** añade configuración y handlers; una línea
  JSON directa es suficiente y más predecible para journald.

# ADR-019 — De motor de ingesta a motor de modelado de datos

- **Estado:** Aceptada
- **Fecha:** 2026-11-12
- **Ámbito:** identidad del proyecto, alcance funcional, hoja de ruta
- **Extiende:** ADR-002 (DuckDB único), ADR-006 (config), ADR-018 (retención/sistema)

## Contexto

Yachay se diseñó como **motor de ingesta**: vigila una carpeta, procesa CSV,
publica Parquet con manifiesto y ofrece API/UI para operarlo. Las 7 piezas del
MVP de ingesta están implementadas y verificadas (2.203 LOC, 194 pruebas, 100%).

Pero el uso real previsto es otro. El usuario final trabaja así:

> «Meto 2-3 hojas de cálculo, quiero **acomodarlas**, **detectar
> inconsistencias**, **hacer comparaciones y cruces**. Lo que hace un motor de
> información.»

Eso **no es ingesta**. Es **modelado de datos**. Y el análisis contra las fuentes
oficiales (IBM, DAMA-DMBOK Cap. 5, Metadata Matters, Microsoft, Kimball) confirma
que un motor de modelado tiene cuatro columnas vertebrales que Yachay **no
cubre**:

1. **Definir** — entidades, atributos, relaciones, claves, notación.
2. **Transformar** — shape, merge, joins, agregaciones, cálculos.
3. **Validar** — contra reglas, estándares, vocabulario, esquema.
4. **Versionar y comparar** — versionado, diff de modelos, linaje.

El §8 del documento canónico («Pipeline determinista») declaraba 5 pasos de
transformación de los cuales **solo 1 está implementado** (lectura cruda). Ese
hueco es precisamente el corazón del caso de uso real.

## Decisión

### 1. Reencuadre de identidad

Yachay pasa de **«motor de ingesta»** a **«motor de modelado de datos local»**.
La ingesta sigue siendo una **capacidad**, no la finalidad. El activo principal
deja de ser el dataset publicado y pasa a ser el **modelo guardado** (esquema +
reglas + cruces) que se reaplica de forma repetible.

### 2. Alcance funcional — nivel 1 completo, parte de 2 y 3

Se adopta un alcance por **complejidad creciente** (de menor a mayor), con los
nombres de la taxonomía validada contra las fuentes:

**Nivel 1 — Triviales (completos):**

| ID | Función | Origen |
| --- | --- | --- |
| B1 | Transform & shape | Microsoft |
| C7 | Perfilado de datos (nulos, duplicados, rangos) | IBM data quality |
| C3 | Estándares de nombres / vocabulario | DAMA, Metadata Matters |
| C4 | Dominios / valores permitidos | IBM (constraints), DAMA |
| B2 | Merge / Append | Microsoft |

**Nivel 2 — Simples (núcleo de definición):**

| ID | Función | Origen |
| --- | --- | --- |
| A1 | Entidades y atributos | IBM (paso 1-2) |
| A2 | Claves (primaria / foránea) | IBM (paso 5) |

**Nivel 3 — Medias (relación y repetibilidad):**

| ID | Función | Origen |
| --- | --- | --- |
| B3 | Joins | Microsoft |
| C5 | Integridad referencial (huérfanos) | IBM data integrity |
| D1 | Diff de versiones | Metadata Matters |
| E4 | Automatización (reejecutar el modelo) | Metadata Matters |

**Total: 13 funciones.** Deliberadamente **fuera** (Niveles 4-5): normalización
formal, modelo dimensional, linaje, capa semántica, gobernanza. Pertenecen a un
«ERwin/PowerDesigner ligero» y no al objetivo.

### 3. Lo que NO cambia

- **Ingesta**: scanner, admisión, cola, estados, leases, reconciliación, GC.
- **Persistencia**: DuckDB único motor (ADR-002), SQLite WAL, Parquet + manifiesto.
- **Auditoría**: toda operación deja rastro; nunca se registran valores de datos.
- **Frontera**: la UI es cliente; la API es proyección; el worker ejecuta.

### 4. Cambio de stack respecto al MVP de ingesta

| Pieza | Antes (ingesta) | Ahora (modelado) | Motivo |
| --- | --- | --- | --- |
| Entrada | CSV en `inbox/` | **Excel `.xlsx`/`.ods` + CSV, elegido por el usuario** | Las hojas no llegan solas; el usuario las aporta |
| Unidad de trabajo | Job | **Modelo** (esquema + reglas + cruces guardados) | El valor es la repetibilidad |
| Núcleo del código | `worker` + `csv_pipeline` | **`model`** (catálogo de reglas y cruces) | Es lo que da la función |
| Motor de transformación | `read_csv_auto` (lectura cruda) | **DuckDB con SQL de transformación** | Joins, agregaciones, pivots |
| Estado | Máquina de jobs (9 estados) | Máquina de jobs **+ catálogo de modelos** | Se conserva la ingesta |
| Cola / leases / systemd | Centrales | **Se conservan** pero dejan de ser el foco | Siguen siendo correctos |

**Implementación actual:** `openpyxl` (`.xlsx`) y `odfpy` (`.ods`) están
declaradas en `pyproject.toml`. Son dependencias de **entrada**, no de
transformación: el contenido se vuelca a DuckDB y el resto del pipeline no cambia.

### 5. Relación con el §8 del documento canónico

El §8 («Pipeline determinista») **sigue siendo válido como objetivo**, pero se
reinterpreta: sus pasos 1-4 (validación, perfil, reglas, alta confianza) son
exactamente las funciones **Nivel 1-2** de este ADR. El paso 5 (ambiguos → LLM)
queda **fuera de alcance**: pertenece al LLM Gateway (§10), que sigue siendo
opcional y no se implementa en esta etapa.

### 6. Qué pasa con cada pieza existente

| Componente existente | Destino |
| --- | --- |
| `worker`, `reconcile`, `gc`, `storage` | **Se conservan**: la ingesta sigue |
| `api` (20 operaciones actuales) | **Se extienden**: endpoints de modelo (definir, ejecutar, comparar) |
| `desktop` (7 vistas actuales) | **Se reorienta**: de «cola de trabajos» a «modelo y resultados» |
| `pipelines/csv_pipeline` | **Se sustituye** por un motor de transformación con reglas |
| `log`, `limits`, `systemd` | **Se conservan** sin cambios |

## Consecuencias

- El proyecto tiene un **objetivo claro y acotado**: 13 funciones, no 35.
- Se reutiliza ~40% del código (persistencia, ingesta, API, UI, infraestructura).
- El 60% restante (modelo, reglas, cruces, diff, Excel) es **nuevo y da el valor**.
- La documentación deja de presentar el proyecto como «solo diseño» (lo era el
  README antiguo, ya desactualizado) y refleja el estado real por función.
- El alcance queda **cerrado por niveles**: lo que no está en la lista no entra.

## Alternativas descartadas

- **Seguir solo con ingesta:** no resuelve el caso de uso real («cruzar 3 hojas»).
- **Construir el motor de modelado completo (Niveles 1-5):** meses de trabajo,
  territorio de herramientas comerciales; sobrepasa el objetivo.
- **Usar una herramienta existente (erwin, PowerDesigner, Power BI):** descartado
  por el usuario; se quiere herramienta propia, local y repetible.
- **Empezar por el LLM Gateway (§8 paso 5):** el LLM elige entre **candidatos
  generados por reglas**; sin las reglas de Nivel 1-2 no hay candidatos que
  ofrecer, así que construiría el techo sin los cimientos.

# ADR-016 — API v1 sobre socket Unix, sin dependencias nuevas

- **Estado:** Aceptada
- **Fecha:** 2026-11-11
- **Ámbito:** `src/motor/api/` (`envelope.py`, `routes.py`, `server.py`),
  `src/motor/limits.py`, `src/motor/__main__.py`, `tests/unit/test_api.py`
- **Fija:** el contrato del §2.2 (superficie) y del §2.4 (envelope y errores),
  que no existía en el repositorio

## Contexto

La fase B pide una API v1 local que exponga el estado del motor y sus
operaciones. El entorno es offline y no instala dependencias nuevas, así que un
stack ASGI (FastAPI, uvicorn) quedaba fuera: no está en `uv.lock` y no se puede
resolver desde la caché local.

La API podía romper tres invariantes ya decididas:

- **Convertirse en un segundo worker.** `reconcile`, `claim_next`, `heartbeat` y
  el pipeline están diseñados para un solo proceso (ADR-007, ADR-014). Una API
  que reclamara o reconciliara duplicaría la autoridad sobre los leases.
- **Abrir una segunda vía de admisión.** El escáner de `inbox/` es la única
  admisión (ADR-008): deriva `job_key`, decide idempotencia y crea el job. Una
  API que insertara jobs podría crear un `job_key` distinto para el mismo
  contenido.
- **Filtrar el interior.** Rutas del sistema de ficheros, leases, `worker_id` o
  valores del dataset en la respuesta convertirían el contrato en un espejo del
  esquema.

Además, el contrato de la API (§2.2/§2.4) no estaba escrito en ningún sitio: solo
existía la intención. Una API sin contrato cerrado no se puede probar ni
versionar.

## Decisión

1. **Transporte: `http.server` de la stdlib sobre `AF_UNIX`.** El servidor es un
   `ThreadingHTTPServer` con `address_family = socket.AF_UNIX`. **No hay listener
   TCP**: la API no es alcanzable desde la red, ni siquiera en `localhost`. El
   socket vive en `<root>/data/motor.sock` por defecto
   (`yachay api [--root] [--config] [--socket]`), con modo `0o660` (operador y
   grupo de servicio), se elimina al cerrar y un socket huérfano de un proceso
   muerto se reemplaza al arrancar. `SIGINT` y `SIGTERM` producen la misma parada
   limpia: un gestor de servicios detiene con `SIGTERM`, y la acción por defecto
   dejaría el fichero del socket en disco.
2. **HTTP/1.1 con `Connection: close` por respuesta.** `HEAD` se resuelve como
   `GET` y el cuerpo se omite (RFC 9110). Un método no declarado sobre una ruta
   existente es 405, no 404.
3. **Envelope único.** Éxito: `{api_version, ok: true, data}`. Error:
   `{api_version, ok: false, error: {code, message}}`. `api_version` es `v1`.
   Los códigos son un conjunto **cerrado**: `bad_request` (400), `not_found`
   (404), `method_not_allowed` (405), `invalid_state` (409),
   `payload_too_large` (413), `internal_error` (500), `unavailable` (503).
   Construir un envelope con un código fuera del conjunto falla en el servidor,
   no en el cliente. El cliente ramifica por `code` y nunca parsea `message`.
   Un 500 dice siempre `internal error`: el detalle no se filtra.
4. **Servidor sin estado.** Una conexión SQLite por petición, ninguna caché,
   ningún estado retenido entre peticiones. SQLite sigue siendo la única
   autoridad (ADR-005) y el worker el único proceso que ejecuta pipelines y toca
   leases (ADR-014).
5. **Superficie cerrada (veinte operaciones).** La superficie creció con M6
   (ADR-019); la fuente sincronizada es `docs/api/openapi.yaml`, que se verifica
   contra las tablas `_STATIC_ROUTES`/`_DYNAMIC_ROUTES` de `routes.py`.
   - Núcleo (ADR-016 original, nueve): `GET /v1/health`,
     `GET /v1/jobs?state=&limit=`, `GET /v1/jobs/{job_id}`,
     `POST /v1/jobs/{job_id}/cancel`, `POST /v1/jobs/{job_id}/retry`,
     `POST /v1/inputs?name=`, `GET /v1/datasets`, `GET /v1/datasets/{run_id}`,
     `GET /v1/datasets/{run_id}/manifest`.
   - Modelado (M6, once): `GET /v1/models`, `POST /v1/models?name=&source=`,
     `GET /v1/models/{model_id}`, `GET /v1/models/{model_id}/runs`,
     `POST /v1/models/{model_id}/runs?source=` (repetible para append), `GET /v1/profile?name=`,
     `GET /v1/models/{model_id}/rules`, `POST /v1/models/{model_id}/rules`,
     `DELETE /v1/models/{model_id}/rules/{name}`, `GET /v1/diff?before=&after=`,
     `GET /v1/orphans?left=&right=&on=`.
6. **Lo que la API no hace.** No reconcilia, no reclama, no renueva leases, no
   ejecuta pipelines y no crea jobs. `POST /v1/inputs` conserva el original en
   `model-inputs/` y publica un hard link en `inbox/`; la admisión sigue siendo
   del escáner (ADR-008), y ambos nombres apuntan al mismo contenido. El worker
   puede retirar `inbox/` sin invalidar los flujos de modelado ni duplicar los
   bytes. Una sola vía de admisión, un solo `job_key`.
7. **Cancelar es cooperativo.** `POST .../cancel` solo escribe
   `cancel_requested` (vía `jobs.request_cancel`) y solo en
   `claimed|queued|running|deferred`; en cualquier otro estado devuelve 409. El
   worker decide cuándo se detiene: la API no mata nada.
8. **Reintentar es explícito (§7).** `POST .../retry` acepta
   `failed|quarantined|cancelled`, exige que el input siga existiendo en disco y,
   en una sola transacción, pone `state = 'queued'`, `attempt = 0` y limpia
   `run_id`, `worker_id`, `lease_until` y `cancel_requested`, dejando el evento
   de auditoría `api_retry_job`. Es el único punto que reutiliza el contador de
   ADR-015, sin campo nuevo.
9. **Transacciones explícitas.** Los handlers de escritura usan un único
   `contextmanager` (`BEGIN IMMEDIATE` → `COMMIT`, o `ROLLBACK` ante cualquier
   fallo). Un rechazo por estado inválido no deja escritura parcial.
10. **El único cuerpo es el fichero de entrada, en crudo.** Un
    `Content-Type: application/json` declarado se rechaza con 400: no hay
    contrato JSON de entrada y aceptarlo guardaría un JSON como si fuera un
    dataset. `Content-Length` inválido o negativo → 400. Por encima de
    `MAX_REQUEST_BYTES` (16 MiB) → 413 tras drenar hasta `MAX_REQUEST_DRAIN`
    (4×): cerrar sin drenar convertiría el rechazo en un EPIPE ilegible. El
    cuerpo se guarda en un `SpooledTemporaryFile` (nunca entero en memoria) y
    `size_bytes` informa de lo que realmente llegó, no de lo declarado.
11. **Escritura atómica y sin carreras.** El input se escribe en
    `<nombre>.part`, creado con `O_EXCL`, se sincroniza con `fsync` y se renombra
    con `os.replace`. El escáner solo ve el fichero completo en el nombre final;
    el `.part` hace de cerrojo, así que dos subidas concurrentes del mismo nombre
    no entrelazan bytes y la segunda recibe 409.
12. **Nombres de fichero.** `^[A-Za-z0-9][A-Za-z0-9._-]{0,199}$`: sin
    separadores, sin punto inicial, sin traversal. Un nombre ya existente → 409;
    nunca se sobrescribe.
13. **Lecturas sin interior.** Jobs y datasets se proyectan a campos explícitos:
    ni `lease_until`, ni `worker_id`, ni `path`, ni `manifest_path`. El detalle
    de dataset sirve el `manifest.json`, que es el commit físico (ADR-004); un
    dataset registrado cuyo manifest falta en disco devuelve 503 `unavailable`
    (no es culpa del cliente, pero el servicio no puede responder).
14. **Salud con dos significados.** `GET /v1/health` devuelve 200 cuando SQLite
    responde y 503 `unavailable` cuando no: un operador debe poder distinguir
    "la base no está" de "hay un defecto". Un 500 queda reservado para lo que el
    cliente no puede accionar.
15. **Un log JSON por petición.** `ts`, `component: "api"`, `method`, `route`,
    `status`, `duration_ms`. `route` es la **plantilla**
    (`/v1/jobs/{job_id}`), nunca el identificador pedido ni una ruta de
    fichero: el log sirve para operar, no para reconstruir datos. La plantilla
    se loguea **también en error**: `dispatch` marca el `ApiError` con la ruta
    ya resuelta, de modo que un 4xx/5xx se agrega por endpoint y no como
    `<unrouted>`.
16. **Mensajes de error en un solo idioma (español).** El `code` es el contrato
    y el cliente ramifica por él, nunca por `message`; pero el log y la consola
    los lee un operador, así que un único idioma evita incoherencias. El 500
    mantiene su mensaje genérico («error interno»): el detalle no se filtra.
17. **Entrada malformada es 400, no 404.** Un identificador no numérico en la
    ruta o en la query es `bad_request`; un id numérico inexistente es
    `not_found`. El cliente distingue «corrige tu entrada» de «no existe».
18. **Un cuerpo vacío no se admite.** `POST /v1/inputs` rechaza un archivo de 0
    bytes con 400: evita que el escáner admita un job que fallaría en el
    pipeline, gastando un intento en un error accionable en la frontera.

## Consecuencias

- Sin dependencias nuevas: el entorno offline sigue siendo suficiente y
  `uv.lock` no cambia.
- La API no puede convertirse en un segundo worker: no hay código que reclame ni
  que reconcilie, y la superficie no los expone.
- Una sola vía de admisión (el escáner), así que la idempotencia por `job_key`
  sigue teniendo un único dueño.
- El retry manual resucita un job agotado con `attempt = 0`: un fallo
  determinista puede reintentarse a mano sin límite. Es deliberado (es la vía del
  §7) y cada intento queda auditado; el tope automático de ADR-015 sigue
  gobernando los reintentos que no pide una persona.
- `GET /v1/datasets/{run_id}` y `.../manifest` devuelven hoy el mismo objeto,
  porque el manifest es el único artefacto servible. Se mantienen separados
  porque el contrato los separa y el segundo puede estrecharse después sin
  romper al primero.
- Un 413 cuesta drenar hasta `MAX_REQUEST_DRAIN`; el coste está acotado y no
  depende del cliente.
- **Autenticación opcional.** Por defecto el control de acceso es el permiso del
  socket (`0o660`) y la ausencia de listener de red. Si se configura
  `YACHAY_API_TOKEN`, la API exige `Authorization: Bearer <token>`; cualquier
  proceso del grupo sin ese token recibe 401.
- **Riesgo declarado: el servidor es multi-hilo.** La escritura de inputs está
  protegida por el `.part` exclusivo y SQLite serializa las escrituras, pero dos
  peticiones de retry simultáneas sobre el mismo job pueden hacer que la segunda
  vea el estado ya cambiado y responda 409. Es el comportamiento correcto, no un
  fallo: la operación no es idempotente por diseño.
- **Riesgo declarado: sin paginación por cursor.** `limit` va de 1 a 500 (50 por
  defecto) con orden fijo; una flota grande exige refinar el contrato, no
  cambiar el transporte.
- La suite (`tests/unit/test_api.py`) habla por el socket real: cubre transporte,
  envelope, jobs, inputs, datasets, frontera y CLI, y el gate
  (`./scripts/test.sh`) mantiene 100% de cobertura sobre `src/`.

## Alternativas descartadas

- **FastAPI/uvicorn:** dependencia nueva, no resoluble offline, y el contrato no
  la necesita: no hay validación de esquema ni documentación automática que
  justifique el coste.
- **Listener TCP en `localhost`:** expone la API a cualquier proceso de la
  máquina y a cualquier contenedor con la red del host; el socket Unix ya acota
  el acceso por permisos de fichero.
- **`POST /v1/jobs` que inserte el job:** abre una segunda vía de admisión y
  duplica la lógica de `job_key` del escáner (ADR-008).
- **Cancelar matando el worker:** la API no conoce procesos y el worker es el
  único dueño del lease; el flag cooperativo respeta ADR-014.
- **Exponer `reconcile`/`claim`/`heartbeat`:** convertiría la API en un segundo
  worker y rompería la propiedad de un solo proceso sobre los leases.
- **Devolver las filas tal cual:** filtraría rutas, leases y valores del dataset;
  la proyección explícita es el contrato.
- **`attempt = attempt + 1` en el retry:** consumiría el presupuesto de ADR-015
  sin que el operador lo vea; el §7 pide un reintento explícito, no otro intento
  automático.
